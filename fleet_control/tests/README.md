# Тесты fleet_control

Тесты работают **вместо UI**: вызывают REST control (`/api/fms/*`) и проверяют, что получилось в
fleet_database (через её REST и gRPC) и в fleet_dispatch (gRPC).

Нужны запущенные:

1. `fleet_control`;
2. `fleet_database` (и PostgreSQL за ним);
3. `fleet_dispatch`.

Большинству тестов брокер и симулятор не нужны: роботы регистрируются с выдуманными `serialNumber`,
dispatch просто подписывается на их топики. Тесты с живым роботом (вся цепочка control → база → dispatch →
робот) регистрируют робота симулятора `ktc/amr1`; если он не выходит на связь за 10 с, они пропускаются.
Перед ними `ktc/amr1` не должен быть зарегистрирован в базе под другим id.

Карта робота симулятора (`map_1`): если её нет в fms, тесты создают её сами и после удаляют; если есть —
берут как есть (нужен хотя бы один waypoint) и не меняют, а `test_availability_follows_maps` пропускается.

Python-классы gRPC генерируются из `proto/*.proto` при каждом запуске (в `_gen/`), отдельный шаг не нужен.

## Таблицу не чистим

У каждого теста свои роботы `test-ctl-<случайное>` (производитель `test`). После теста они удаляются из
dispatch и из базы, чужие записи тесты не трогают. Если прогон оборвать (Ctrl+C), могут остаться записи
с производителем `test`:

```bash
psql postgresql://fms:fms@127.0.0.1:5432/fms -c "DELETE FROM robots WHERE manufacturer = 'test'"
```

Карты — так же: `test-ctl-map-<случайное>`, удаляются через `DELETE` control (чтобы и граф в памяти control
не остался). Оставшиеся после обрыва — удалить и перезапустить control:

```bash
psql postgresql://fms:fms@127.0.0.1:5432/fms -c "DELETE FROM maps WHERE map_id LIKE 'test-ctl-map%' OR map_id ~ '^map-[a-z0-9]{6}$'"
```

Миссии удалить через API нельзя (история). Тесты отменяют свои миссии после себя, а в конце прогона удаляют их строки из базы через `psql` (адрес — `DATABASE_URL`, по умолчанию `postgresql://fms:fms@127.0.0.1:5432/fms`). Остались после обрыва прогона:

```bash
psql postgresql://fms:fms@127.0.0.1:5432/fms -c "DELETE FROM missions WHERE mission_id LIKE 'test-ctl-m-%'"
```

## Установка

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Запуск

Из папки `fleet_control/tests`:

```bash
.venv/bin/python -m pytest -v
```

## Настройки (переменные окружения)

| Переменная | По умолчанию | Что это |
|---|---|---|
| `CONTROL_HTTP` | `http://localhost:8003` | REST fleet_control |
| `DATABASE_HTTP` | `http://localhost:8002` | REST fleet_database |
| `DATABASE_ADDRESS` | `localhost:5002` | gRPC fleet_database |
| `DISPATCH_ADDRESS` | `localhost:5001` | gRPC fleet_dispatch |
| `VDA_MANUFACTURER` / `VDA_SERIAL` | `ktc` / `amr1` | Робот симулятора для тестов с живым роботом |
| `VDA_MAP_ID` | `map_1` | Карта робота симулятора |

## Что проверяется

| Файл | Что |
|---|---|
| `test_robots.py` | `POST /robots`: ответ 201 в формате контракта, робот в базе и в dispatch, `name` по умолчанию = id, проверка полей (400 `INVALID_INPUT` с `details`, все ошибки сразу), не JSON, 409 на занятый id и тот же физический робот; `PATCH /robots/{id}`: имя и метки, неприсланное не меняется, `name: null` → id, `id`/`manufacturer`/`serialNumber` не меняются (400), неизвестный робот → 404 |
| `test_robot_commands.py` | `DELETE /robots/{id}`: 202 с `PENDING_DELETE`, после этого робота нет ни в базе, ни в dispatch, повторный DELETE → 404, можно зарегистрировать заново; pause/resume неизвестного робота → 404. С симулятором: зарегистрированный робот выходит ONLINE в базе, pause → `status.paused`, resume; DELETE при миссии → 409 `ROBOT_BUSY`, с `?force=true` → 202 и миссия `FAILED ROBOT_REMOVED` |
| `test_fleet_sync.py` | Сверка с dispatch (каждый тест до ~15 с): робот, записанный в базу в обход control, появляется в dispatch; удаление, прерванное на `PENDING_DELETE`, доводится до конца — робота нет ни в базе, ни в dispatch |
| `test_mission_run.py` | Миссии едут (M-3c), с двумя роботами симулятора `ktc/amr1` (на a) и `ktc/amr2` (на d) на своей карте `map_1` (a ─ b ─ c ── d): миссия с действием — назначена ближайшему, выполнена, шаг и действие `COMPLETED`/`FINISHED` с временами, робот снова `IDLE` на узле цели; к d едет amr2, к a — amr1; два шага по порядку; `requestedRobotId` важнее близости; вторая миссия ждёт занятого робота и уходит ему, когда он освободится; `HIGH` уходит раньше стоящей перед ней `LOW`; отмена во время действия — `CANCELING` → `CANCELED`, робот свободен, повторная отмена — 409; отмена посреди ребра — робот `NOT_READY` «between nodes», после `position` снова `IDLE`. «Скоро свободный» (c1b): робот, которому осталось только ехать, получает миссию раньше далёкого свободного — как следующую, назначена до конца текущей, начата после; с действием впереди — не кандидат; текущую отменили — следующая уходит в очередь и другому роботу; отмена следующей — сразу `CANCELED`, текущая доезжает. Маршруты для Live Map (c2, `GET /routes` control): пока робот едет — оставшийся путь шага (`released`, узлы и рёбра), цели шагов, `planned` пуст; проехал узел — он отрезан; стоит на цели с действием — линии нет; второй шаг — `stepIndex` 1 и свой путь; у скоро свободного — `nextMissionId`, у самой следующей маршрута нет; доехал — маршрута нет; чужая карта — пусто, без `mapId` — все. История (c3, события в базе): выполненная миссия — `QUEUED` → `ASSIGNED` (робот и причина «… s to the first step») → `RUNNING` → шаг → действие `FINISHED` → шаг → `COMPLETED`, по порядку и с роботом; отмена в пути — `CANCELING` с причиной, потом `CANCELED`; следующая миссия (c1b), у которой отменили текущую, — `ASSIGNED` «after its current mission», `QUEUED` с причиной от amr1, потом `ASSIGNED` amr2. Без симулятора или при существующей `map_1` — пропускаются |
| `test_missions.py` | Миссии (M-3b): `POST /missions` — 201 в `QUEUED`, все поля контракта, документ в базе = ответ, свой id или `m-xxxxxxxx`, приоритет, действия с параметрами и `requestedRobotId` сохраняются, станция без рёбер — через узел взаимодействия; ошибки полей → 400 `INVALID_INPUT` с путём до поля (`steps[1].actions[0].actionType`) и все сразу, ничего не сохранено; неизвестные карта, узел, робот → 400; станция, до которой не доехать, → 400; нет пути между шагами → 400 `INVALID_MISSION`; повтор с тем же id — 200 и та же миссия (и для завершённой — из базы), другой запрос с тем же id — 409, 5 одновременных одинаковых POST — одна миссия; отмена в очереди — 202 `CANCELED`, шаги `CANCELED`, в базе то же; повторная отмена — 409, неизвестная — 404; история в базе по карте и состоянию; события (c3): создание — одно `QUEUED` с `at` = `createdAt`, отмена из очереди — `CANCELED` с причиной «canceled by operator», без событий не начатых шагов |
| `test_maps.py` | Карты (M-1): `POST /maps` — 201, в базе то же, что в ответе; свой id (= mapId робота) или сгенерированный `map-xxxxxx`; 409 на занятый id; поля → 400 `INVALID_INPUT`; каждая ошибка графа → 400 `INVALID_MAP` с текстом и все ошибки сразу, ничего не сохранено; предупреждения не мешают; пустая карта; неизвестные поля документа сохраняются; `version`, время, `zoneSet` ставит сервер. `PATCH` — частичная замена, картинка прежняя, замена и удаление картинки, устаревшая версия → 409 `VERSION_CONFLICT` с `currentVersion`, 5 одновременных PATCH — проходит один, проверка полей и графа, id не меняется, 404. `DELETE` — 204, потом 404, можно создать заново; с симулятором — карта, на которой стоит робот, → 409 `INVALID_STATE`. Карта на 5 МБ — POST и PATCH (лимиты HTTP и gRPC). Последствия сохранения (M-3b): `maxSpeed: 0` → 400; ловушка (в тупик заехать можно, выехать нельзя), остров и станция, до которой не доехать, → 409 `CONFIRMATION_REQUIRED` со списком, ничего не сохранено, с `?force=true` — сохраняется; то же для `PATCH`; с симулятором — удаление узла, на котором стоит робот, → 409 с id робота |
| `test_availability.py` | Готовность робота в `GET` базы: выдуманный робот (никогда не выходил на связь) — `OFFLINE` с причиной, availability записана сразу после регистрации. С симулятором: робот на узле графа — `IDLE` без причин, pause → `PAUSED`, resume → `IDLE`, миссия → `BUSY` |
